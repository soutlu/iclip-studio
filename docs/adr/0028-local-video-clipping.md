# ADR-0028：视频裁剪拼接是生成域里的一家本地 provider

- 状态：已接受（2026-09-15）
- 关联：[ADR-0004](0004-generation-queue-in-postgres.md)（排队、状态机与不重投规则不变，本文只多一条队列）、[ADR-0018](0018-video-generation-mirrors-upstream.md)（`POST /generations/video` 不变；上游没有区间编辑参数这一事实是本文的前提）、[ADR-0022](0022-uploads-without-registry.md)（产物只交回地址，不登记）、[ADR-0020](0020-generation-metadata.md)（编辑链的坐标走 `metadata`，不建表）

## 背景

视频编辑要改的是成片里的某一段。上游两家（万相 3.0、Seedance 2.5）都没有区间参数：输入是一条完整的参考视频加一句提示词，输出是一条全新的视频。把整条成片发上去按时长计费，改 4 秒要付 15 秒的钱，还会顶上万相「输入 + 输出 ≤ 30 秒」的账。

所以区间语义只能落在本系统：把要改的那一段切出来发给上游，拿回改好的片段，再拼回去。切和拼都要 ffmpeg。

前端做不了这两件事。视频地址是上游对象存储的（ADR-0018 §5），浏览器读不到字节——连 canvas 抽帧都会被跨域挡住，更不用说切片；而且切出来的片段必须是一个上游能拉取的地址，前端就算切得动也还要上传一次。

## 决策

### 1. 切和拼是同一个操作，一个端点

`POST /generations/clips` 收一串 `segments`，按顺序裁出 `[start, end)` 拼成一条。切参考片段是传一段，合成成片是传整条的所有段——没有第二个端点，也没有第二套实现。

### 2. 落在生成域，是一家本地 provider

产物是一条视频、一次耗时的后台加工、要查状态、要归属到对话与需求单——和一次生成同形。所以它是 `generation_jobs` 里的一行，`provider` 是 `ffmpeg`，走既有的队列、状态机与 `event.generation.changed`。

新增第三个 `kind`：`clip`。**不复用 `kind=video`**：`request_from_payload` 按 `kind` 选校验模型，而它的 `request` 是 segment 列表不是 `VideoGenerationIn`；分开之后 `GET /generations?kind=video` 也不会被中间素材和成片挤满。

它是 provider 协议里的同步那一支（和图片一样），`submit` 一次调用出结果，没有轮询阶段。

### 3. 单独一条队列

ffmpeg 占 CPU，别的提交队列都在等网络。按 ADR-0004 §3「谁会拖住谁」的切法，它自己一条 `generation-submit-ffmpeg`，并发默认 2，不进配置——和视频那条同理，只有一家。

### 4. 切不重编码，拼一定重编码

切参考片段走 `-c copy`：省一次编解码，也避免中间素材反复转码掉画质。代价是 `-c copy` 只能在关键帧处下刀，起点会落到请求区间之前最近的那个关键帧，产物比区间长，多出来的主要在开头；尾部也会因 B 帧延迟多出几帧。**不在服务端补偿**：调用方拿产物的实际时长反算起点，误差是几帧的量级，参考片段只是给模型看的上下文，服务端为这几帧再解一遍码不值。

**参考片段不下载整条源**：地址直接交给 ffmpeg，由它用 HTTP Range 只读索引与选区（实测 27 MiB 的源传约三成）。源忽略 Range 时退化为顺序读：moov 在文件头部仍出正确产物；在尾部则 ffmpeg 退出码为 0 却不产出内容，由产物检查判失败。读取量由索引、关键帧和选区决定，选区接近整片时也接近整片，所以只约束产物大小，不约束累计流量。

拼成片一定重编码：各段来自不同来源（原片与模型还回来的片段），画幅、帧率、音轨都不保证一致，`-c copy` 的 concat 分离器要求输入参数一致，走不通。真跑实测：720×960 25fps 的输入，Seedance 2.5 还回来是 834×1112 24fps——比例照旧是 3:4，分辨率档位与帧率变了。**成片对齐到原片**，插进去的片段缩放去适配它，不反过来让成片尺寸跟着上游的档位漂。哪条是原片按素材整条时长认：原片是完整的一条，模型还回来的只有被编辑那一段的长度，不管区间选多长原片都更长；按各段在成片里贡献的时长认不行，区间一超过一半就认反。这样不用调用方多传一个字段。有一段带音轨就出音轨，没音轨的段补等长静音。

### 5. 产物只交回地址，参考片段与成片分前缀

照 ADR-0022：不登记、不发 id，桶里一个对象加一条生成记录就够了。参考片段存 `video-clips/`，成片存 `video-masters/`——分前缀是为了让桶的过期规则只作用在中间素材上，成片长期保留。过期规则本仓改不到，由部署侧配。

### 6. 编辑链不建表

三条记录属于哪条出片，写在记录的原作号 `root_job_id` 列里（ADR-0032）：生成域知道「这是衍生记录、根是谁」，据此不把它算进审计，分叉时让它跟着根一起进副本（ADR-0029 §3）。「哪一版基于哪一版、改的是哪个区间」仍是调用方的坐标，走 `metadata`（ADR-0020 决策 1），与图片编辑记 `sourceUrl` 同一形状。生成域不认识「版本」这个概念，版本列表由前端从链上的成片投影。

### 7. 模型怎么触发编辑，前端按模型名认

上游两家触发编辑的方式不同（万相靠正文里的意图词，Seedance 2.5 靠 `provider_options` 里的开关），上游没有任何接口交代这件事，所以得有人告诉调用方。放在前端一张按模型名匹配的表里（`video-editor.api.ts`）：编辑器只列表里认得的模型，提交 `POST /generations/video` 时按表加前缀或选项。

服务端对「编辑」一无所知：`media_generation.video.allowed_models` 仍只是允许表，`GET /generations/video-models` 仍只回模型 id，`POST /generations/video` 不替任何模型拼任何东西。代价是上游改词、加模型要发版而不是改配置重启；这类变动少，换来配置形状不变、部署不用改，值。曾经把它做成配置里的 `models`/`edit` 声明（2026-09-15，#353），因为每个模型都要多写一行、不写就不能编辑，开发者判断做复杂了，同日撤回。

**不支持的画幅同理，前端按模型名认。** 上游同样没有接口交代某个模型不接受哪些画幅（万相 3.0 不收 21:9），选了就要等记录变 `failed` 才知道。分镜页的出片表单按模型名维护一张「已知不支持」表（`storyboard/video-model-support.ts`），把那几个画幅在下拉里灰掉；没列到的一律放行，交上游判。服务端不声明画幅，`video-models` 仍只回 id；表在前端而不在配置，理由与编辑触发同一条。

**不声明素材规格。** 参考视频的时长、大小、格式上游自己就拦，照 ADR-0018 §2 不在本系统复制一份。

## 取舍

- **接受**：进程在 ffmpeg 跑到一半时中断，这条任务按 ADR-0004 §5 判 `SUBMIT_INTERRUPTED` 失败，不自动重投。对不计费的本地加工这偏保守，但换来一条不用分情况讨论的恢复规则；重发一次的成本是几秒。
- **接受**：产物整份读进内存再交给对象存储（`put_public_object` 只收 `bytes`）。片段小，成片是几十兆的量级。
- **接受**：每次合成都要把涉及的源整条重新拉一遍（参考片段不拉，见决策 4）。拼接走 `concat` 滤镜，编码期会在各路输入上来回读，三路远程输入按需读不划算。段数不会随编辑次数增长：成片本身是一条完整视频，下一次编辑从它上面切，所以任何一条成片都只有基底前段、编辑片段、基底后段这最多三段、两个地址。上限 50 段只是挡畸形请求。
- **不做**：把上游成片转存到本系统的桶。那会推翻 ADR-0018 决策 5，收益（缩略图、下载、跨域）另开一轮算。
- **不做**：给切片做精确到帧的重编码切割。要精确就得解码整段，而参考片段只是给模型看的上下文，多几帧上文不影响它改哪里；对齐由调用方按实际时长处理。
