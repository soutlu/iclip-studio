# ADR-0001：视频领域按操作建模——一张 `generation_jobs`，一行一次操作，镜头组按编号认

- 状态：已接受（2026-09-25）
- 取代现行实现中的做法：#303 与 #401（镜头组编号升为列，查询、分组不再读 `metadata`；衍生记录在原作号之外再记直接来源）、#305（上传确认落一行，外部地址仍不登记）、#353（参考片段不落行，切片与合成由服务端按编辑段完成，`/generations/clips` 下线）。
- 沿用：#466（分叉不拷记录，副本按血缘继承祖先已完成的记录）；替人办事（持 `users:act_as` 的钥匙按 `user_name` 换属主）。
- 影响：[CONTEXT.md](../CONTEXT.md) 术语「分镜」「镜头组」「成片」「生成任务」「审计口径」；合同 [§10 上传](../../contract/conventions.md#10-上传-uploads)、[§11 媒体生成](../../contract/conventions.md#11-媒体生成-generations)、[§12 审计报表](../../contract/conventions.md#12-审计报表-audit)、[§13 资料库](../../contract/conventions.md#13-资料库-library)；[openapi.json](../../contract/openapi.json) 的 `/generations/*` 与 `/uploads/*`。

## 背景

一条生成记录是什么角色，靠 `kind`、`root_job_id`、`request.purpose`、`metadata` 四个信号组合推出来。审计、资料库、分叉、下载、对话视频抽屉、编辑链、帧图历史七处各推一遍，推法不完全一致。

镜头组没有稳定身份：分镜页按位置认第几镜，服务端按 `metadata.shot` 认，重新切分后两边对不上。

同一个词指几样东西。「镜」既是镜头组，也是时间线上的一段；「成片」既指出片，也指编辑后合成的新版；「帧」既是镜头组里的第 N 张图，也是任意一张生成的图。

编辑与版本的语义只在前端。哪几条记录属于一次编辑、合成基于哪一版、V1/V2 怎么排，都由 `edit-chain.ts` 从 `metadata` 的 `editId`、`baseEdit`、`editStart`、`editEnd` 拼出来，服务端不知道。没合成的编辑段调用了模型，却没有服务端认得出的形状。

系统依赖的字段藏在 JSONB 里：审计按 `metadata->'shot'` 数镜、按 `request->>'user_name'` 归人，资料库从 `provider_snapshot->'durationMs'` 取时长。键名一改，这些读口静默失效。

## 决策

### 1. 以操作为中心：一行就是一次操作

调用了模型就记一行，产出了我们持有字节的媒体就记一行。参考片段、编辑过程中的中间状态、标注草稿不记。

一行是哪种记录，由 `kind`、`operation` 和有没有来源直接决定，不再从别的信号推：

| 记录 | `kind` / `operation` | 来源 `source_job_id` |
|---|---|---|
| 出片、重出 | video / generate | 无 |
| 编辑段 | video / generate | 基底成片 |
| 合成 | video / compose | 编辑段 |
| 图片生成 | image / generate | 无 |
| 帧图编辑 | image / generate | 底图（外部底图见 §4） |
| 切图 | image / cut | 那张宫格 |
| 上传 | video 或 image / upload | 无 |

`operation` 只说怎么执行：调模型（generate）、本地拼接（compose）、本地切图（cut）、用户上传（upload）。编辑段和帧图编辑也是 generate，和出片、图片生成的区别在于基于库里的哪一行，而不是有没有输入。`kind` 不再有 `clip`：合成出来的是视频，谁执行看 `provider`。切图、上传创建即完成。

### 2. 镜头组按调用方给的编号认，不设 id

分镜（`video_shot.json`）是一段对话当前的出片方案，由镜头组按顺序组成。镜头组就是调用方传的编号，传什么就是什么。它升为列 `shot_index`，与公开接口的请求字段同名：出片由调用方给，可空；编辑段、合成从原作复制。请求里的 `shot` 字段是镜头组的结构化内容，不是编号。

分镜之下：镜头是时间线上的一段；镜头帧是镜头组里的第 N 张，指向一张图片，正文里用 `@ImageN` 引用；图片是生成或上传的图，放进镜头组才叫镜头帧。出片记录存的是提交时的请求，之后分镜怎么改都不影响它。

### 3. 成片与版本：按原作分组，现算不存

成片是一个镜头组名下完整、可播放的一条视频：`kind = 'video'`、已完成，且是无来源的 generate（出片）或 compose（合成）。编辑段都有记录，没合成的、失败的也有，但不是成片。

每条视频行挂在一条原作上：出片的原作是自己，编辑段、合成的原作是 `root_job_id`，链仍只有一层。版本组是原作的（对话，`shot_index`）；原作没有 `shot_index` 时自己一组。组内成片按 `finished_at` 编 V1、V2……，重出和合成都往后排，读时现算。

分叉沿用 #466：副本读得到祖先已完成的记录，但不拥有它们。在副本里剪继承来的出片，合成那行属于副本，版本归源那一组；副本自己出的片是副本的组。

### 4. 直接来源一列，原作一列

`source_job_id` 记这一行直接基于库里的哪一行，可以指向继承来的祖先记录。受理时校验来源可见、已完成，且在本对话或它继承的范围内；帧图编辑按地址对上的上传行不属于任何对话，不受对话范围限制，仍按主体可见范围判断。

#401 以「成片有基底与编辑结果两个输入，单亲列表达不了」否掉过直接父记录。现在两个输入沿链表达：合成的来源是编辑段，编辑段的来源是基底成片，区间记在编辑段上，单亲够用。`root_job_id` 保留，用于分组。

`source_url` 只给一种行用：帧图编辑的底图是外部地址，比如历史宫格的格子、历史上传，它们没有行。帧图编辑的 `source_job_id` 与 `source_url` 恰好填一个；其余行不填 `source_url`。

### 5. 编辑与合成由服务端完成

编辑段有自己的入口：调用方给基底成片的任务号、区间、正文、模型。服务端按关键帧切出参考片段（放在已配过期规则的 `video-clips/` 前缀下，按编辑段的任务号命名，不落行）交给模型，`range_start_ms` / `range_end_ms` 记实际切出来的区间，不是请求的数。基底必须是可见、已完成的成片，区间在基底时长之内，一次改一段。

合成只传编辑段的任务号：服务端按它的基底和区间算出前段、编辑段、后段再拼接，新版本归原作那一组。`/generations/clips` 下线，`metadata` 里的 `editId`、`baseEdit`、`editStart`、`editEnd` 不再需要。

### 6. 帧图编辑以底图的记录为锚

锚点是底图对应的那条记录，不是分镜里的第几格。那条记录可以是图片生成、切图、上传，或上一次帧图编辑。请求带 `sourceUrl`，服务端按地址找行：先找本对话及继承来的产物，再找上传行；找到记 `source_job_id`，找不到记 `source_url`。采用时这一格必须仍是编辑者当时看到的那张；已有成片不受影响。

为让锚点都有行可指：上传确认时落一行 upload；agent 出宫格时宫格一行，每格再落一行 cut，来源是那张宫格。上传确认按 `uploadId` 幂等：行 id 就用签名时发的 `uploadId`，重复确认返回同一行。上传模块不依赖生成域，落行通过它声明的端口交给生成域，由 app 层装配。

图片的来历顺着 `source_job_id` 往上走，只剩 `source_url` 的是外部起点。帧图历史的兄弟行：库内底图按同一 `source_job_id` 找，外部底图按同一 `source_url` 找。

### 7. 系统依赖的做列，系统不解释的进 JSONB

判据是谁在读，不是字段多少。查询、分组、索引、外键、约束要用的做列；只有执行方或调用方自己读的进 JSONB。

- `request`：只存发给执行方的输入，整份存取，改为可空（上传行没有请求）。`user_name` 留在里面，只作发给上游对账的输入。
- `metadata`：调用方自己的标签，服务端不读不写、原样存取，与 Stripe 的 metadata 同一用法；分镜页的 `frame` 留在这里。`shot_index` 不再折进 `metadata.shot`，镜号只在列里。
- 作者：属主 `owner_user_id` 的用户名，不另加 `user_name` 列。浏览器会话的名字必须是自己的；持 `users:act_as` 的钥匙按名字把属主换成对应账号，没有就建占位账号；用户名唯一且设定后不改。所以名字与属主一一对应。新增的编辑段、合成入口和出片一样，先定名字、再换主体、后受理；上传确认的名字可选，给了才换主体，不给就记在当前主体名下。
- 时长：`duration_ms` 升为列，不再从 `provider_snapshot` 里读。

### 8. 外部地址不登记

只有我们持有字节的媒体落行：生成的、切出来的、上传的。调用方传入的外部参考图、参考视频仍以地址留在 `request` 里，不转存、不建行。

### 9. 表的终态：27 列

表名仍是 `generation_jobs`。现有 22 列删 2、加 7：

- 谁做的、属于哪：`id`、`owner_user_id`、`api_key_id`、`conversation_id`、`task_id`、`shot_index`（新）。上传行没有对话。
- 做什么：`kind`（只剩 `video` / `image`）、`operation`（新）、`provider`、`request`（改可空）。
- 基于什么：`source_job_id`（新）、`source_url`（新）、`root_job_id`、`range_start_ms` / `range_end_ms`（新，两个整数列）。
- 结果与状态：`status`、`output_url`、`watermark_output_url`、`duration_ms`（新）、`error_code`、`error_message`、`provider_task_id`、`provider_status`。
- 时间：`created_at`、`submitted_at`、`finished_at`。
- 标签：`metadata`。
- 删除：`updated_at`（无人读）、`provider_snapshot`（时长提出后只剩排障用途，且含上游签名地址）。

每种行的必填与留空由组合 CHECK 约束兜底：编辑段必有来源、原作、区间；合成必有来源、原作；切图必有来源；帧图编辑两种来源恰好一个；区间只出现在编辑段；上传没有请求与来源。新增三个部分索引：视频行上的（`conversation_id`, `shot_index`）、`source_job_id`、图片行上的（`conversation_id`, `output_url`）。

### 10. 口径都从这张表直接算

- 可下载：成片。
- 审计出片次数：同组无来源的 video / generate 行，含失败与在途；编辑段不计，副本不计。
- 资料库：一组一张卡，卡面是最新一版，时长读 `duration_ms`，作者是属主的用户名。
- 对话在出片：这段对话下未到终态的视频行，编辑段、合成一起算。

### 11. 合同

外部调用方用的出片、出图、查询接口只加不改：已有的请求字段和返回字段含义不变，`shot_index`、`task_id` 照旧收，新字段一律可选。唯一收窄的是 `metadata.shot`：镜号只认 `shot_index`，调用方自己写进 `metadata` 的 `shot` 不再被当作镜号；`metadata` 本身照旧原样存、原样回显。

- 新增编辑段、合成两个入口（见 §5）；帧图编辑请求加可选的 `sourceUrl`。
- 上传确认落行，请求加可选的 `userName`。
- `GenerationOut` 加 `operation`、`shotIndex`、`sourceJobId`、`sourceUrl`、区间；时长改读列，字段不变。`kind` 不再有 `clip`：带它的只有前端发起的本地加工记录，迁移后改记 video / compose。
- 列表筛选加 `operation`、`shotIndex`、`sourceJobId`；`event.generation.changed` 帧加带 `operation`、`shot_index`（帧沿用协议的 snake_case）。
- `/generations/clips` 只有前端用，随编辑段、合成入口上线下线。改合同的 PR 同时带上前端重新生成的类型。

### 12. 存量按切片迁移

迁移按切片分成几个版本，每个版本与切换对应写入方、读取方的代码同一次落地，不留过渡期的兼容代码。每个版本都是先加列，再回填、清掉迁走的 `metadata` 键，最后收紧非空、组合约束和索引。回填规则：

- 删参考片段行（线上数据已确认可删）；`clip` 改成 video / compose。
- 出片的 `shot_index` 取 `metadata.shot`，编辑段、合成取原作的。
- 编辑段的来源按 `baseEdit` 找那次合成，没有就是原作；合成的来源取同一 `editId` 下在它之前创建的最新编辑段，找不到就带 id 报错终止。
- `metadata.sourceUrl` 对得上库里的行就填 `source_job_id`，否则进 `source_url`。
- 时长从 `provider_snapshot.durationMs` 提出，之后删 `provider_snapshot`；`updated_at` 直接删。
- 属主校正：2026-09-15 替人办事启用前，钥匙提交的行属主是钥匙主人，`request.user_name` 才是真人。把两者不一致的行的属主改成同名账号，没有账号的按替人办事的规则建占位账号。
- 迁走的键：`shot`、`editId`、`baseEdit`、`editStart`、`editEnd`、`sourceUrl`。

## 取舍

- **接受**：一张表装两种生命周期。上传、切图创建即完成，提交、轮询、错误那几列天然为空；27 列在生产系统里是常见宽度。
- **接受**：镜头组没有 id。重新切分后，同一编号下的新旧成片连着算。
- **接受**：删掉的参考片段行和 `provider_snapshot` 降级回不来；排障时看不到上游原始回包，只剩 `provider_status` 与错误码。
- **接受**：「对话在出片」变宽，编辑段、合成在跑时对话也算在出片。
- **接受**：不持 `users:act_as` 的钥匙不换属主，它提交的行作者是钥匙主人，名字只发给上游。线上网关用的钥匙持有这个权限。
- **接受**：校正属主后，早期钥匙行的属主与所在对话的属主不同；对话属主不回填。
- **接受**：不传 `shot_index`、只在 `metadata.shot` 里写镜号的调用方，以后落的是没有镜号的出片。与网关的约定本来就是 `shot_index`，前端随本决策改传它。
- **接受**：上传确认的 `userName` 可选，不带名字的钥匙上传记在钥匙主人名下。
- **不做**：以资产为中心（素材表，生成任务引用素材）。创作由一次次操作构成，要回答的是「这张图怎么来的」「这一版基于哪一版」，操作记录直接回答；资产表要双写，还要和任务表对账。上传、切图以操作行落在同一张表里。
- **不做**：按生命周期拆表，把上传、切图单独放一张。宽度是一张表两种生命周期的代价；拆开后每个找来源的查询都要跨表合并。
- **不做**：镜头组 id。镜头组是分镜下的产物，编号由调用方定。
- **不做**：记录编辑的中间状态、参考片段、标注草稿。只记调模型的编辑段和最终成片。
- **不做**：登记或转存外部地址。
- **不做**：区间用 `int4range`。两个整数列，读写直接。
- **不做**：`user_name` 列。与属主重复。
- **不做**：改表名。
