# ADR-0015：视频上传按内容去重，同一个文件只留一个地址

- 状态：已接受（2026-10-07）
- 不取代已有 ADR。
- 影响：[CONTEXT.md](../CONTEXT.md) 的「上传」词条、[contract/conventions.md](../../contract/conventions.md) §10；后端 [uploads/service.py](../../server/src/iclip/domains/uploads/service.py) 的确认用例、[generation/service.py](../../server/src/iclip/domains/generation/service.py) 的 `SettledRecords`、[object_store/store.py](../../server/src/iclip/platform/object_store/store.py) 的端口，以及迁移 `0023`。

## 背景

资料库要加参考视频，参考视频按视频地址一条一行，所以同一个视频文件必须只对应一个地址。现在每次上传都按 `uploadId` 落一个新对象、交回一个新地址：桶里 584 个视频上传只有 218 个不同的文件，366 份是重复上传，按地址认不出它们是同一条视频。

浏览器直传是一次整传（PUT），对象存储给这种对象（对象类型 `Normal`）的 ETag 就是文件的 MD5；确认时本来就要读对象的元信息，指纹顺带拿到，不用下载视频。核对过桶里 584 个视频上传，全是 `Normal`，抽查的 MD5 与 ETag 一致。

比较过的方案：只按地址认同一条视频，每次上传照旧一个新地址；确认上传时按文件指纹认出重复，交回已有的地址。

## 决策

1. **确认时按 MD5 认重复。** 文件照样传上来；确认视频上传时，对象类型是 `Normal`、ETag 是 32 位十六进制，就把它的小写作为 MD5 记在上传记录上（`content_md5`，库里由约束限定只有视频上传行有）。同一个 MD5 已有视频上传时，这一行的地址落最早那条（按建立时刻、id）的地址，本次传上来的对象删掉。
2. **不分属主。** 同一个人、不同的人传同一个文件，都交回最早那份的地址。每次上传仍记一行，属主、钥匙、id 照记本次的；按地址找「本人的上传」先按属主筛，一个地址可以有几行。
3. **重复确认交回记录上的地址。** 先按 `uploadId` 查记过没有，记过就不再读本次的对象（去重后它已经删了）；类型与大小读那个地址上的对象：记了 MD5 的，是同一个 MD5 最早那条视频上传传上来的对象；没记 MD5 的，就是这次自己的对象。
4. **删不掉不影响确认。** 删除失败只记一条 warning，确认照常交回共用的地址。
5. **只认一次整传。** 对象类型不是 `Normal` 时 ETag 不是 MD5，不记 MD5、不去重，照旧交回本次的地址。

## 取舍

- **接受**：重复的文件照样传一遍，确认后才删；上传的流量与时间省不下来。
- **接受**：同一个文件的两次首次确认同时发生时，可能都找不到对方，各留一份地址。不加锁；之后再传这个文件，按最早那条去重。
- **接受**：别人先传的地址交给后来的人用。地址本来就是公开的，记录照记各自的属主。
- **接受**：删除失败时多留一份字节，只占空间，不影响任何地址。
- **不做**：图片去重。
- **不做**：合并已经重复的存量上传。它们没有记 MD5，各留各的地址；之后再传其中某个文件，也认不出它们，新传的那份成为最早的一条。
- **不做**：外部网站的视频地址去重，仍按地址认。
