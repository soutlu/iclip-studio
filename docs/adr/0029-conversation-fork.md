# ADR-0029：对话分叉是种子快照加出片记录拷贝，不复制运行记录

- 状态：已接受（2026-09-16）
- 关联：[ADR-0011](0011-context-compaction.md)（压缩只改模型窗口）、[ADR-0013](0013-transcript-protocol-freeze.md)（Transcript 是运行事实的投影）、[ADR-0020](0020-generation-metadata.md)（调用方自带的坐标标签）、[ADR-0021](0021-conversation-soft-delete.md)（软删与墓碑）、[ADR-0026](0026-conversation-usage-ledger.md)（对话用量台账）、[ADR-0027](0027-audit-reports.md)（审计报表）
- 修订 [CONTEXT.md](../CONTEXT.md) 术语「对话」补分叉；合同新增 [§6 分叉](../../contract/conventions.md#分叉)，[§12](../../contract/conventions.md#12-审计报表-audit) 补一条排除；迁移 `0009_conversation_fork`。

## 背景

治理者要拿用户跑过的对话做对照试跑：换个说法、换个 Agent 重来一遍，看结果差在哪。他本来就读得到所有人的对话（`users:manage`），但所有写口都硬限属主——没有任何位置能让他在别人的对话里发一条消息，也不该有。

现成的 `:regenerate` 只能在自己的对话里重跑末轮，而且会把原来那一轮丢掉。要的是「从第 N 轮岔出一条自己的路，原对话不动」。

## 决策

### 1. 分叉是「读源 + 建自己的对话」，不是跨属主写

`POST /conversations/{id}:fork` 对源只走已有的读可见性（`_readable`，治理者含墓碑），产出的新对话属主是调用者。源对话一个字节都不改，所以不需要新权限词，也不破坏「行级归属与操作权限分别判断」。因此它是通用能力而不是管理员后门：人人能分叉自己的，治理者能分叉任何人的。

### 2. 副本只写一张种子快照，不复制运行记录

历史重建只读 `latest_conversation_snapshot`（`TranscriptHistory.read`），`TurnRewind.commit` 已经示范了怎么把截断后的消息存成一张新快照。分叉是同一个动作换个 `conversation_id`：把源快照截到第 N 轮，`run_id` **原样保留**，写成副本的第一张快照。

`list_events(run_id)`、`get_run`、`tool_effects` 都按 run_id 全局查，所以副本读继承轮时，每轮的终态、错误与子代理面板都从源那几行只读解析出来，一行运行记录都不用复制。这避开了另一条路的全部成本：`runs` / `events` / `snapshots` / `agent_job_runs` 的主键重铸，以及 `snapshots.messages` 与 `tool_effects.effect_summary` 里内嵌 run_id 的批量改写。

代价写在合同里：副本下没有 `agent_jobs` 行，所以继承轮 `:regenerate` 是 `404`，源对话里跨多次运行的一轮在副本里会拆成多轮显示。

### 3. 连出片记录一起拷，只拷根记录

分镜页的结果条不在工作区里，是 `GET /generations?conversationId=` 查出来的。不拷它，副本打开就是「提示词表满的、帧和视频全空」，要测编辑得先花钱把每个镜头重出一遍——正好撞上「付费外部调用不得自动重投」。

所以复制 `status = 'completed'` 的记录：换新 id 与新 `conversation_id`，属主记分叉者（结果条按属主可见性查），`api_key_id` 置空，`request`（含 `user_name`）、`metadata` 与四个时间戳原样保留——坐标是结果条的定位键，时间戳决定同一坐标下哪条算最新，改成当下会把副本后来自己出的片压下去。

排除两类：视频编辑链（`metadata.rootJob`，各条靠 root 的 id 认亲，根在副本里换了 id 就连不回去）与本地加工（`kind = 'clip'`，参考片段在桶上配了过期规则，拷过去迟早是死地址）。副本继承的是分叉那一刻已确认的成片，不继承编辑的版本历史。

### 4. 分五步写库，对话行最后写

`conversations`、`workspace_files`、`materials`、`generation_jobs`、`snapshots` 归四个存储，各开各的事务，没有统一回滚。表之间没有外键，任何顺序都合法，所以选一个中途失败也无害的：工作区 → 素材 → 出片记录 → 种子快照 → 对话行。对话行没落库的副本进不了任何列表、读不出 transcript；拷进去的出片记录按属主仍查得到，是查得到却没人用的孤儿行。

源没闲下来就拒绝（`409`），口径与 `:regenerate` 相同（在跑、等审批或排队都算）——比对话活动里的 `busy` 严一格，因为排队中的那条一起跑就会写新快照，轮号跟着变。

### 5. 副本不进审计报表

拷来的出片记录带着源的 `request.user_name`，算进去会把原作者的产量重计一遍；副本自己跑的也是试验数据。`forked_from IS NULL` 挡在 `videos` / `person` / `runs` 三个根 CTE 与 `missing_shot` 上，其余口径都从它们派生。

## 取舍

- **接受**：工作区文件与出片记录没有逐轮历史，拷的是分叉那一刻的那一份。从第 3 轮分叉，agent 的上下文停在第 3 轮，却可能读到第 6 轮写的 `video_shot.json`。`:regenerate` 对单轮已经默认接受这件事，分叉到任意轮只是更显眼。
- **接受**：拷来的出片记录丢掉了「原来那次是钥匙发起的」这一点（`api_key_id` 置空）。副本是浏览器动作，源那几行的 `api_key_id` 一个没动，审计归因仍在源上，不违反「key 行为必须可审计」。
- **接受**：副本工作区的文件版本从 1 起。版本号是给那一份做乐观锁的，跟着搬会让副本的首次写对不上。
- **不做**：顺着 `forked_from` 让副本读源的出片记录。那要让生成域在查询时读 conversations 表，是这个项目花了几篇 ADR 避开的方向，还附带「祖先记录按分叉时刻过滤」和多级分叉的多跳问题；拷行在分叉那一刻就把这些冻住了。
- **不做**：复制运行记录并重铸 run_id。见决策 2。
- **不做**：副本继承源的需求单。挂上就是认领，那会动到别人的单子。
- **不做**：复制媒体字节。对象存储没有删除接口，key 按任务 id 生成，编辑只产出新地址；两边共享同一批对象，谁也毁不掉谁的。
- **不做**：接受调用方铸的副本 id。分叉先拷数据、最后落对话行，没有可供幂等重放的位置。
