# ADR-0007：资料库标签维度下支持最多三级标签取值

- **状态**：已接受（2026-10-21）
- **取代关系**：取代 [ADR-0006](0006-library-tags-as-data.md) 第 1 条中的「两级取值上限」，其余决策全部沿用
- **影响范围**：[CONTEXT.md](../CONTEXT.md)「标签」；[contract/conventions.md](../../contract/conventions.md) §15；[architecture.md](../architecture.md)

## 背景

在实际运营分类中，「场景」等维度需要表达如 `城市通勤与生活 → 早晚高峰通勤 → 地铁/公交拥挤站立 (防滑/耐脏)` 这样完整的三级层次。原定的两级上限会丢失细分场景；而如果强行把父级名称拼进子级标签名里，又会导致标签管理、按上级联动筛选和 AI 打标各自去切分字符串。

## 决策

1. **维度下扩展为最多三级取值**：顶层维度本身不计入级数，其下最多允许创建三级子标签。底层依然复用现有的 `parent_id` 自关联表结构，无需新增表或字段。
2. **递归生成 AI 打标约束与去重**：标签管理、人工打标、列表筛选与 AI 自动打标统一消费这棵三级树。AI 打标时将父子层级递归编码为嵌套 JSON Schema 约束；当模型选中下级标签时，落库时自动剔除其所有祖先标签，只保存最细粒度的叶子/子级标签。
3. **动态维护**：三级场景标签的名称与层级完全由管理员在后台维护，不写死在代码中；修改树结构同样不触发存量条目自动重打标。

## 取舍

- **接受**：前端标签管理与选择器需要支持展示三级树结构，后端 AI 打标的 Schema 生成与结果解析改为递归处理。
- **不做**：不通过字符串拼接模拟层级，不单独为「场景」建专用表，也不放开为无限层级。
