# ADR-0021：对话删除只做标记，`conversation_ids` 保留表下线

- 状态：已接受（2026-09-12）
- 关联：[ADR-0017](0017-client-minted-record-ids.md)（决策 2「id 不得重新分配」的落地方式由本文修订，对外语义不变）、[ADR-0008](0008-activity-from-agent-jobs.md)（活动状态仍由票据算出，对话域只收 id 集）
- 合同 [§6 对话](../../contract/conventions.md#6-对话-conversations)不改：删除后重用 id 仍是 `404`。

## 背景

ADR-0017 要求对话删除后 id 不得再发给任何人，因为运行历史按对话 id 保留。当时的做法是另立一张 `conversation_ids`：创建时先在它上面认领 id，再写对话行；删除时物理删对话行，保留表里的 id 留着。

一件事记在两张表上。`conversation_ids` 里只有一个 UUID，不知道属主、不知道 Agent，与对话行也没有外键；创建要先认领再写入，两条语句才等于一次插入。这次收拢库表，「需求单 → 对话 → 对话的视频和图片」里对话只该是一张表。

## 决策

### 1. `conversations` 加 `deleted_at`，删除改为标记

删除流程不变：先清工作区与素材台账，再改对话行，只是最后一步从 `DELETE` 变成 `SET deleted_at = now()`。行留着占住 id，运行历史照旧按 id 找回。

### 2. 领域层只见活着的行

仓储每条读写语句都带 `deleted_at IS NULL`，包括治理者的审计列表、需求单下的尝试列表、按 id 直读、改名、换归属、`touch_run` 与自动起名。`Conversation` 数据类不加字段：已删除的行不进入领域层，对它的任何操作都是 `NotFound`，再删一次是 `404` 而不是静默的 `204`。四个索引都改成只收活着的行。

### 3. 幂等创建直接在对话行上冲突

`create_if_absent` 对 `conversations.id` 做 `ON CONFLICT DO NOTHING`：没插进去就按属主回读，命中自己活着的那一段答 `200`，已删除或属于别人一律 `NotFound`。ADR-0017 决策 2 的三条语义（`404`、不交给撞 id 的人、创建失败不占 id）一条不少，只是不再需要第二张表。

### 4. 属主外键从 CASCADE 改成 RESTRICT

已删对话的行也占着 id；若删用户级联把它们带走，id 就放出去了。今天没有删用户的路径，这一条把「删用户须先明确处置他的对话」写进约束，而不是留给将来的人发现。

### 5. 存量墓碑从票据找回

`conversation_ids` 里对话行早没了的 id，属主与 Agent 只剩 `agent_runtime.agent_jobs` 里有：迁移 `0003_conversation_soft_delete` 按票据补一条 `deleted_at = now()` 的对话行，属主与 Agent 取最早那条票据，时间取票据首尾。没有任何票据的 id 直接丢——挡重用是为了保护运行历史，这些 id 没有历史。然后删表。

## 取舍

- **接受**：墓碑行带着标题、归属列等没有意义的字段。它们只占 id，没有读口会碰到。
- **接受**：治理者的审计列表看不到已删对话。今天没有「复盘已删对话」的需求；要做时是在审计接口上加筛选，不是把墓碑放回所有读口。
- **接受**：票据的 `conversation_id` 是文本列，回填时把 UUID 转成文本去比，不把文本转成 UUID；脏数据只会匹配不上，不会中断迁移。属主已不在 `users` 的票据同样跳过，否则外键会让整次迁移失败。
- **不做**：恢复已删对话的接口。`deleted_at` 让它成为可能，但不是这次的需求。
