# ADR-0016：图片生成按模型选择

- 状态：已接受
- 关联：[ADR-0004](0004-generation-queue-in-postgres.md)（生成队列与一家一条提交队列）

## 背景

图片生成原先只有一家模型，选择这件事没有表达位置：请求里没有模型字段，能出什么画幅与分辨率由全局枚举决定，唯一可选的轴是那家自己的渠道（dev / pro）。接第二家之后这三条都不成立——各家的画幅档、分辨率上限、有没有渠道轴都不同。

## 决策

### 1. 可选集合的事实源是装配表，不是一份白名单

运行配置的 `media_generation.image.models` 声明接入了哪几家；受理层按它校验，能力清单端点按它对外声明。**不另写一份 `allowed_models`**：视频需要白名单是因为模型名是自由字符串直接透传给同一家，白名单是唯一防线；图片的模型名是代码里有适配器的那个有限集，再写一份 YAML 白名单就是第二份会漂的事实源。

点了没接入的那家返回 `422`，**不回落到默认那家**——付费调用不替调用方换参数（[CONTEXT](../CONTEXT.md) 不变量 10）。

### 2. `model` 落 request JSON，`provider` 列由受理层同时写

一个字符串两处：JSON 那份是对外可见的请求快照（`GET /generations` 直接带回去，前端不用另查接口就能标出哪家出的图），`provider` 列是队列的分派键与审计依据。**唯一写入点在受理层**，别处不许回填或改写任何一份。

`GenerationOut` 因此不加字段——它明确不外露 `provider`，而调用方要的信息已经在 `request.model` 里。

### 3. 画幅与分辨率枚举取并集，按家在受理层校验

`IMAGE_ASPECT_RATIOS` 与 `IMAGE_RESOLUTIONS` 保持各家的并集，不按家收窄成多个 `Literal`。同一个 `TypeAdapter` 还要回读历史行，把业务规则写进请求模型会让老记录读不回来。

各家真正支持的范围由适配器上的 `ImageModelSpec` 声明，**受理层与能力清单端点读的是同一个对象**，不可能一边声明支持一边拒绝。校验必须在受理层：留给适配器的 `submit` 去拒，那已经是一行排过队的失败任务，而上游若先扣费再校验，这一次就白花了。

代价是对外合同上能填的组合多于真能跑的组合，能力清单端点与那几条 `422` 共同兜底。

### 4. 能力声明写在代码里，不进配置

Seedream 没有 4k、少两档画幅，这是模型自带的事实，不是部署选择。配置管的是「接哪几家、路由段、并发」。

### 5. `channel` 留在对外合同上，改成可空

两个渠道价钱不同，选哪个是调用方的决定。声明了渠道轴的那家省略时按它声明的默认档填；给没有渠道轴的那家传 `channel` 返回 `422`，而不是接受并忽略。

### 6. agent 出图钉死用哪家，写在代码里

出图工具要 4k 整图切格、依赖 dev→dev→pro 的渠道重试，这些只有特定几家给得了；而产品接口的默认模型是另一件事，换了它不该带着出图链路一起换。所以模型名钉在 `capabilities/shot_video/generation.py` 的常量里，跟旁边已经钉死的分辨率与渠道并排，**不开配置项**——将来要按工具分、或让模型自己选，改那一行或把它提到工具签名上即可，不用清理一个作废的配置键。

配套两道检查，性质不同所以落点不同：

- 钉的那家能不能满足出图要的档位与渠道 —— 纯代码事实，单测拦，CI 就红。
- 配置有没有真的接入这家 —— 只有运行期知道，挂 shot_video 之前 `RuntimeError`。

## 取舍

- **接受**：模型名在适配器常量与出图常量两处出现且没有 import 关系，靠单测钉住两者一致。让 `capabilities` 直接引 `domains.generation` 会破坏依赖边界。
- **接受**：能力清单端点的画幅与分辨率对外是字符串数组而不是枚举。声明存的是有序元组，顺序即全局枚举的顺序，不随集合哈希漂。
- **不做**：跨模型自动重试或兜底。换家等于多一次计费还换画风。
- **不做**：让模型面工具自己选家。模型看不到价格、配额与画风一致性，逐次选家还会破坏同一批的连戏。
