# ADR-0005：开跑记录运行也发 `event.session.updated`

- 状态：已接受（2026-10-01）
- 取代 [ADR-0004](0004-align-realtime-protocol-with-kimi.md) 第 5 条中「开跑只改 `lastRunId`，不发 `updated`」；该条其余内容沿用。
- 影响：[合同 §5「全局帧」](../../contract/conventions.md#全局帧)的生命周期帧表；对话域 `begin_run`；前端对话行池的收尾标记与未读判定。

## 背景

运行开跑时，服务端在一次写入里记下最近一次运行 `lastRunId`、抹掉属主的收尾标记 `completedAt`，这次写入不发帧。客户端只能从开跑的活动帧推导「收尾标记已空」，并把这个推导值记在活动帧的序号上。

活动帧在开跑写入之前发出。两者之间读出的行（列表重拉或单行补读）带着旧的收尾标记，`lastSeq` 又不小于活动帧的序号，合并时会把推导出的空值复原；此后没有别的帧来纠正，收尾标记一直错到下一次读行。未读判定要的新 `lastRunId` 也只能靠补读拿到。

Kimi 的做法是会话元数据一变就发 `sessionUpdated`。

## 决策

开跑记录运行与改名、换归属、标收尾一样，是一次行变化：`begin_run` 写入之前取水位，写入后读出整行，提交后广播 `event.session.updated`。帧带新的 `lastRunId` 与被抹掉的收尾标记，信封序号在提交后另发，比行内 `lastSeq` 大；客户端按信封序号记这两个字段的水位，窗口期读出的旧行盖不掉它们。

## 取舍

- **接受**：每次运行开跑多一帧全局帧，与活动帧同一投递范围；审批后续跑也算一次开跑。
- **接受**：活动帧之后、`updated` 到达之前，客户端仍显示推导出的空收尾标记与旧的 `lastRunId`，`updated` 一到即对齐。
- **不做**：让活动帧携带 `lastRunId`。活动帧的投递在队列提交之后、运行记录写入之前，那时还没有新的 run id；把两件事合成一帧要改运行驱动的提交次序。
