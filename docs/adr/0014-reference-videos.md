# ADR-0014：参考视频一条视频一行，拆解存在 Postgres，品类自己维护

- 状态：已接受（2026-10-07）
- 不取代已有 ADR。
- 影响：[CONTEXT.md](../CONTEXT.md) 的「参考视频」「资料库」词条、[architecture.md](../architecture.md) 的参考视频一段与持久化表、[contract/conventions.md](../../contract/conventions.md) §14 参考视频；后端 [domains/references/](../../server/src/iclip/domains/references/)、[app/reference_breakdown.py](../../server/src/iclip/app/reference_breakdown.py)、迁移 `0024_reference_videos`。

## 背景

资料库要能收用户自己上传的参考视频：后台拆解成文档、自动打上片子类型与产品品类两组标签，人能查看、修改、重新拆解。AI 导演在对话里用 `breakdown_video` 拆的视频，也要在这里看得到、改得动。导演那边原来的做法是把拆解按地址摘要存进公开桶，所有对话共用，取不到只当没拆过。

比较过的方案：一次上传一行、一段对话里的一次拆解一行，还是一条视频一行；每次拆解留一份历史，还是只留当前一份；拆解接着存对象存储，还是存进 Postgres；品类读 PDM 品类表、在仓里冻一份 PDM 的副本，还是自己维护一份清单。

## 决策

1. **一条视频一行，上传与对话共用一份拆解，不留历史。** 行按视频地址认（同一个文件上传时已合成一个地址），属主是上传的人或第一次拆它的人；资料库上传与导演的拆解读写同一行，不分来源。只留当前那一份拆解：重拆成功就覆盖拆解与标签，失败保留原来的；人改过的也会被重拆覆盖。
2. **拆解存在 Postgres，不再存对象存储。** 拆解正文、标签、状态与失败原因都在 `reference_videos` 这一行上，状态跳转都是带条件的更新；拆解是业务事实，要能改、要带版本号、要能按全文筛，桶里的一个对象做不到。导演改走这一行之后，公开桶里的共用拆解不再写、也不再读。
3. **品类脱离 PDM，自己维护。** 清单是 PDM 品类表的全部第四级（鞋和配饰，48 个）照抄一份，再加 8 个服装，存的就是名字；以后增删改名都在仓里改，连带处理已经打上的标签。PDM 只有鞋和配饰、没有服装，而参考视频里服装是常见的主推商品；不能为了用 PDM 忍受它的缺陷。「PDM 款目录」词条里「名称字典留在上游、本仓不冻副本」只管款目录的编码归属，不管参考视频的品类。

## 取舍

- **接受**：一份拆解所有人共用，谁改了、谁重拆了，别的对话以后拿到的都是新的那份；已有对话用它工作区里那份，不受影响。
- **接受**：没有历史，覆盖掉的拆解找不回来；重拆前由界面提醒会覆盖。
- **接受**：品类清单与 PDM 从此各走各的，PDM 加了第四级这里不会自动跟上。
- **不做**：一次上传或一次对话拆解一行。同一条视频会拆好几遍、付好几次钱，资料库里也会出现好几条一样的。
- **不做**：保留每一次拆解的历史版本。现在没有对比或回滚的需求，版本号只用来防并发覆盖。
- **不做**：拆解接着存对象存储、表里只放地址。改、带版本、按全文搜都要回到表里，两处存放还要对齐。
- **不做**：读 PDM 品类表或冻一份 PDM 副本。PDM 没有服装，冻副本也补不上；要补就得自己维护，不如整份自己维护。
