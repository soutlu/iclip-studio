# ADR-0004：实时协议与客户端恢复对齐 Kimi，只在确定更优处偏离

- 状态：已接受（2026-10-01）
- 沿用 Kimi Code 的 Transcript 协议与 `subscribe_v2` 订阅（[合同 §5](../../contract/conventions.md#5-agent-对话-transcript)）；对照的是本机安装的 Kimi Code 桌面 1.0.2（内置后端 2.0.1）。
- 影响：[合同 §5、§6](../../contract/conventions.md#5-agent-对话-transcript)；[architecture.md](../architecture.md) §5；[openapi.json](../../contract/openapi.json) 的 `ConversationOut`、`TranscriptPage`、`OpsCatchup` 与 `GET /conversations/{id}`；前端 Transcript 读取与对话列表同步。

## 背景

项目沿用了 Kimi 的 Transcript 协议，但客户端读取顺序、断档恢复与列表同步是自己写的，与 Kimi 的现行实现有多处不同。核对后发现两类问题。

一是我们自己的缺口：打开对话时先订阅、后读基线，服务端对不带水位的首订回 reset，客户端因此每次都多读一次基线；批次号在进程重启或实时状态淘汰后重新编号，而续订只按序号判断能否补发，客户端水位落在新编号范围内时，新流的批次会被接到旧内容上，且不报错。

二是列表同步：全局帧不带属主，治理者的连接收全平台的帧，客户端只能靠「缓存里有没有这一行」猜是不是自己的对话；没有会话生命周期帧；HTTP 列表晚到时会盖掉更新的帧状态。

开发者定的原则是：默认照 Kimi 的做法；只有能说清「Kimi 那样做在我们这里一定更差」时才偏离，每处偏离写明理由。

## 决策

1. **客户端先读基线，再带水位订阅**（照 Kimi）。浏览器先 `GET .../transcript`，再用页上的 `seq` 与 `stream_epoch` 发 `subscribe_v2`，服务端从补发日志接着发。断档或 `append` 位置对不上时，重读基线后带新水位重订，这是唯一的恢复路径。浏览器不调 `/transcript/ops`；端点保留给机器调用方（Kimi 后端同样保留、Web 不用）。
2. **Transcript 实时流带 epoch（偏离：Kimi 的 Transcript 流没有）。** 每次建流生成新 epoch，进程重启、淘汰后重建都算。续订时 `transcript_since` 与 `transcript_epoch` 都对得上才补批；只给序号或 epoch 对不上一律回 reset。理由：Kimi 桌面端的前端与内置服务一起重启，我们是浏览器还开着、服务端重启，运行按数据库续跑（CONTEXT 不变量 6）。重连退避最长 30 秒，足够新流越过旧水位，只看序号会把新批次接到旧内容上。Kimi 自己的会话事件日志就用 epoch 防这件事，这里把同一机制用到 Transcript 流上。
3. **会话事件水位**（照 Kimi 的会话事件 `epoch + seq`）。全局帧与文件变更帧的信封带这段对话的事件序号 `seq` 与进程 `epoch`；`ConversationOut` 带 `lastSeq` 与 `eventEpoch`。规则：
   - 事件帧在写入提交之后发新号，`created` / `updated` 也是事件帧（Kimi 的 `sessionUpdated` 同样带日志序号）；文件变更不论有没有连接订着都占号，客户端不按序号连续性判断丢帧；
   - 列表与单行接口在读库之前取水位，作行上的 `lastSeq`；
   - `created` / `updated` 帧里整行的 `lastSeq` 在写入之前取，比帧自己的信封序号小。

   由此，序号不大于 `lastSeq` 的事件行里已经有了，大于的以帧为准，客户端按字段比较合并：行内事实字段（`activity` 以外）按 `created` / `updated` 的信封序号记水位，`activity` 按行内 `lastSeq` 与 HTTP 行同一口径。写入之前读库的旧 HTTP 行，`lastSeq` 严格小于随后那帧的信封序号，晚到也盖不掉帧带来的事实；若这类帧不另发号、与旧行同号，两边打平，旧行会把新事实盖回去，之后也没有帧来纠正。行内水位必须取在写入之前：写入与取水位之间提交的事件，若被算进水位，行会被当成比它新，而行实际更早。
4. **序号只在进程内存，按对话连续递增，不落库（偏离：Kimi 把事件日志持久化）。** Kimi 持久化是为了按游标重放，我们不做重放（第 6 条），持久化的日志没有读者。合并只需同一进程内单调，加 epoch 区分进程；这与 Transcript 批次号同一口径，单 worker 部署。
5. **会话生命周期帧**（照 Kimi 的 `event.session.created/updated/deleted`）。新建（含替人办事）、分叉副本发 `created`；改名、换合集、换需求单、标或取消收尾（含提交出片抹掉收尾标记）发 `updated`，带整行；删除发 `deleted`。保留 `session.meta.updated`，与 `updated` 并存，Kimi 也是两者并存。不加 `archived` 与 `usage_updated`：我们没有归档概念，列表也不显示用量。开跑只改 `lastRunId`，不发 `updated`，客户端在活动变化后按 id 取单行（照 Kimi），为此新增 `GET /conversations/{id}`。
6. **全局帧带 `owner_user_id`（偏离：Kimi 是单用户，没有这个字段）。** 治理者的连接收全平台的帧，没有属主就分不清别人的对话；已实测会让治理者侧栏随别人每跑完一轮重拉。
7. **不收 `client_hello`，不重放全局事件；重连后用 REST 整份对账（偏离：Kimi 用游标重放已订阅会话的事件）。** Kimi 的重放只覆盖它订着的约 4 段会话，重连后的基线对账也只合并已有行的活动字段，断线期间的新建、删除、改名都不保证恢复。我们重拉全部列表，再按第 3 条合并，覆盖面是 Kimi 的超集。
8. **客户端两处有意不照搬 Kimi。**
   - 重复批次不把连接水位写小：Kimi 会把续订水位写成更小的号，只会多补发或被迫重读，没有任何场景需要回退。
   - 子代理流的空 reset 不直接应用：Kimi 的子代理池直接应用 reset，而我们的 reset 从不带历史轮，照搬会清空已显示的子代理内容；改走主流对空 reset 的处理，退避后重读基线。
9. **已有的产品决定不随对齐改变。**
   - 搜索留在服务端：Kimi 是先把全部会话分页拉到本地再匹配，多用户、会话很多时不可行。
   - 未读记 `lastRunId`：Kimi 只在页面开着、看到运行结束时才标；我们关页再开也判得出。
   - 列表按 `createdAt` 排序（合同 §3）、`busy` 与 `videoGeneration` 分开（CONTEXT「对话」）：这两条是合同与领域定义，不属于本次对齐。

## 取舍

- **接受**：过渡期内，没带 `transcript_epoch` 的旧客户端每次带水位续订都会收到 reset 并整页重拉，包括重连、以及在同一段对话里加订子代理时整表重发；功能正确，只是多读几次基线。
- **接受**：机器调用方调 `/transcript/ops` 不带 `stream_epoch` 时只按序号判，服务重启后分不出重新编号的批次；合同写明，由调用方决定是否带。
- **接受**：`created` / `updated` 帧与 REST 行里的 `activity` 读于写入之后，可能比序号更大、随后到达的 `work_changed` 新，也可能更旧；客户端按行内 `lastSeq` 合并 `activity`，会短暂保留较旧的事件值，下一帧事件到来即纠正。这与 Kimi 的合并语义相同。
- **接受**：事件水位快照要复制一份按对话的序号表，大小随进程运行期间有过事件的对话数增长，与实时投影自己的表同一量级。
- **不做**：单个全进程计数器给所有对话发号（快照只需一个数）。按对话计与 Kimi 一致，换成全局计数器没有正确性上的收益。
- **不做**：持久化会话事件日志与 `client_hello` 游标重放。没有读者，且覆盖面不如 REST 对账。
- **不做**：保留浏览器端的 `/transcript/ops` 补批作为第二条恢复路径。先读基线后订阅之后，同一连接内不会断档，两条路径只会让要测的状态翻倍。
