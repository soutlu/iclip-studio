# ADR-0004: 媒体生成的排队与轮询落在 Postgres 上

- 状态：已接受（2026-08-24）
- **[ADR-0001](0001-architecture-foundations.md)**：Postgres 是唯一事实源，是本文的前提。

## 决策

### 1. 排队交给 procrastinate，事实留在自己的表里

「谁该跑、几点跑、几个同时跑、进程死了谁发现」交出去；「这次提交算不算数、不知道发没发出去时怎么办」留下。`iclip.generation_jobs` 是一次生成的事实，`public.procrastinate_*` 是排期机械，清空它只丢排期、不丢任何事实。它的表落在 `public` 而不是 `iclip`：它的 SQL 全是不带 schema 的裸名字，不认 `search_path` 参数。它自带的建表 DDL 原文冻在迁移 0005 里，**以后每次升级它都要把它新增的迁移脚本抄成一个新 revision**；版本精确 pin。

### 2. 提交也在后台，不在 HTTP 请求里

`POST /generations` 只做校验和落一行 `pending`，返回 202；调外部接口是后台那几条队列的事。于是「提交完已是终态」（同步的图片接口）和「提交完还要等」（两段式的视频接口）是同一段代码的两个分支。

### 3. 三条队列，各自一个 worker

按「谁会拖住谁」切成图片提交、视频提交、状态轮询三条，并发按「纯等待」定（各 100）。数据库连接只在状态跳转时开合。图像转存那一步是真正的天花板：`oss2` 是同步 SDK，包在 `asyncio.to_thread` 里，受默认线程池（约 `CPU+4`）限制；上传成为瓶颈时要显式配执行器，不是调这里的并发。

**周期任务必须 defer 到有 worker 消费的队列上**——排到别的队列（包括它默认的 `builtin`）会永远躺在那儿，而且不报错。所以捡卡死任务的周期任务挂在轮询队列上。

### 3a. 「还在跑」借重试通道走，一个生成只占一行

任务抛 `StillRunning`，由我们自己的重试策略决定「5 秒后再来」：机械上走重试通道，语义上不是失败。**这个策略不许设次数上限**，上限由任务体的守卫给——轮询撞上总时限就写终态并正常返回，提交重读那行看见 `submitting` 就判失败并正常返回。

### 3b. 「还在跑」按固定间隔再问，不做逐次拉长的退避

间隔固定（默认 5 秒）。**唯一按更长间隔重排的情况是「问不通」**（网络断了、对方 5xx）。固定间隔没有自我收敛的性质，所以 `job_timeout_seconds` 是必需的兜底。

### 4. 时刻一律取数据库的时钟

多台应用服务器的时钟差几秒，而这些时刻要拿去对账。

### 5. 不知道发出去没有，就判失败，绝不重投

两家接口都没有幂等键，重投一次就是重复付一次钱。所以：

- 调 provider **之前**先把状态落成 `submitting`。
- **任务被重跑时，第一件事是重读那一行**：还是 `submitting` 就判失败并写清原因，绝不重新提交。这次写入带状态守卫（只在它还是 `submitting` 时才落）。「重跑是安全的」靠这个守卫，不靠「不会重跑」。
- 提交阶段的失败一概是终态，连「网络超时」这种看着可重试的也不重试。
- **不替调用方换参数。** 模型（视频）与渠道（图片）都由请求带来；错误码只负责让人分清「送到了没有」，不驱动任何自动动作，也不做失败后自动换渠道的回退。

### 6. 进程死掉之后，任务怎么回来，分两种

- **优雅关停**（发版、重启）：宽限期到了会打断还在飞的任务，被打断的任务抛异常结束，重试策略把它重排回待办。宽限期不设无限。
- **硬杀**（SIGKILL、OOM、机器没了）：任务留在「有人在做」上，那个 worker 的心跳停了。procrastinate 自动维护心跳，但不会自动重跑（`get_stalled_jobs` 只是查询，`retry_job` 是一次手动调用），所以有一个每分钟跑一次的周期任务干这件事。

**信号处理器归 uvicorn**，起 worker 时必须显式关掉 procrastinate 的（它默认装）。

### 7. 落行与排队不是原子的，所以排队失败要照实说

行走 asyncpg、队列走 psycopg，两个驱动就是两个事务。排队这一步失败就把那行判失败（`QUEUE_DEFER_FAILED`）并把错误抛给调用方；崩在两步中间就留下一个没有任务的 `pending` 行，由人重新发起。**不为此建对账扫描**——事实不完整时把决定权交回人，与 `SUBMIT_INTERRUPTED` 同一条道理。

### 8. 图片结果转存成自己的公开对象

图片接口给的是会过期的签名 URL，所以生成一到手就下载转存到公开对象存储，库里存转存后的地址。

## 权衡

- **接受**：多一个数据库驱动（psycopg 与 asyncpg 并存）、多 30 个数据库对象、以及「升级它就要抄一个新 revision」这笔永久的维护费。换来的是那 400 行调度机械不再由我们维护。
- **接受**：入队不是事务性的（见 §7）。这也是 Postgres 队列最大的理论优势我们享受不到的地方。
- **接受**：轮询是拉模式，结果最晚会晚一个固定间隔（默认 5 秒）才被发现。改成 provider 回调会更即时，但那要开一个公网入口并处理它的鉴权与重放，本轮不值得。
- **接受**：worker 跑在 API 进程里。多进程本来就安全（心跳 + 领取都在库里），所以「以后拆成独立 worker 进程」是个部署选择，不是重新设计。
- **接受**：`submitting` 卡住的行会被照实判成失败，需要人来重新发起，不会自愈。这是刻意的——自愈的代价是可能重复计费。
- **接受**：视频结果直接存 provider 给的地址，不转存；图片转存是因为它明确会过期。
