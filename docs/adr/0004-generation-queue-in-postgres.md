# ADR-0004: 媒体生成的排队与轮询落在 Postgres 上

- 状态：已接受（2026-08-24）
- **[ADR-0001](0001-architecture-foundations.md)**：Postgres 是唯一事实源、Redis 可整段丢掉，是本文的前提。
- **[ADR-0003](0003-detached-runs-and-replayable-streams.md)**：那一份处理的是「一次 agent 运行的事件怎么给人看」；本文处理的是「一批外部生成任务怎么推进」。两者都是「活儿不绑在 HTTP 请求上」，但机制不同：那边是 Redis 里的事件流（可丢），这边是 Postgres 里的行（不可丢）。

## 背景

视频和图片生成都是外部接口，而且两家的形状差得很远：

- **视频**是两段式的：提交拿一个任务 id，之后自己去轮询，一次生成几分钟。
- **图片**是同步的：一次 POST 等到图出来，最长几分钟，没有任务 id。它返回的还是会过期的签名 URL。

产品预期是同时在跑大量生成任务。于是要回答三件事：待办放哪儿、谁去推进、怎么不把钱付两遍。第三件事没有任何组件能替我们答——两家接口都没有幂等键。

## 决策

### 1. 排队交给 procrastinate，事实留在自己的表里

分工是一条线切开的：**「谁该跑、几点跑、几个同时跑、进程死了谁发现」交出去；「这次提交算不算数、不知道发没发出去时怎么办」留下。**

- `iclip.generation_jobs` 是一次生成的事实：谁发起的、发给了谁、到哪一步、结果是什么。
- `public.procrastinate_*` 是排期机械：这件事还没做完。**清空它只丢排期，不丢任何事实**，所以 ADR-0001 那条「Redis 可整段丢掉」的同类要求在这里仍然成立——事实一直在 Postgres 里，而且在我们自己的表里。

**为什么不用 Redis 系的队列**（arq / SAQ / Celery / taskiq-redis 这些）：一个已经受理、可能已经计过费的生成任务是业务事实，而本仓的不变量说 Redis 可以整段丢掉且不损失任何事实。把待办放进 Redis 就破了这条——而且真要补，补法就是「扫业务表找超时未推进的行」，那正是自己写的领取查询，等于既付了组件的钱又留着轮子。

**为什么不自己写。** 第一版是自己写的：`SELECT ... FOR UPDATE SKIP LOCKED` + 一对租约列 + 三条流水线，估的是四十行，长出来 413 行。而在它长出来的过程中连着改了四个缺陷，其中三个都在**调度机械**这一层——一批里混进图片就把同批视频按住五分钟、一张图在飞后到的图要等它整个做完、「等在飞的跑完」写成了等所有流水线于是把切开的三条又焊回去。这些恰好是任务队列库现成给的东西。不是写得特别差，是这个轮子的辐条比估算里多得多。

换过来之后删掉的正是那一层：租约与它的最坏耗时估算、心跳、并发闸门、取任务排期、那圈循环。**留下的一行没少**：`generation_jobs` 照旧是我们的事实表，「不知道发出去没有就判失败、绝不重投」照旧是我们写的判断，「还在跑」在它的重试模型里也照旧不是失败——我们自己实现重试策略来表达这件事。

顺带一个真正的收获：**心跳判活把「租约估多长」这个问题整个消掉了。** 自己写的时候，租约必须盖住整批最坏耗时（图片 600 秒 + 余量），而估短了就是把一次已付费的成功判成失败——那正是四个缺陷里的一个。心跳是按 worker 算的，跟任务多长无关：一个正在做 300 秒图片提交的活 worker 每 10 秒报一次心跳，永远不会被误判。

**代价，说清不含糊：**

- **多一个数据库驱动。** procrastinate 只支持 psycopg，本仓其余部分走 asyncpg——同一个库，两个驱动、两个连接池。（它还只声明 `psycopg[pool]`，那个 extra 不带 libpq，所以我们显式要 `psycopg[binary]`，否则装完 import 就炸。）
- **落行与排队做不到一个事务里。** 这是上一条的直接后果，也是 Postgres 队列最大的理论优势（业务行与任务同生共死）我们享受不到的原因。处置见 §7。
- **建表 DDL 要手工并。** 它自带 4 张表 + 3 个类型 + 9 个索引 + 18 个函数 + 7 个触发器，而本仓规定建表只走人工 Alembic。所以它的 `schema.sql` 原文冻在迁移 0005 里，**以后每次升级它都要把它新增的迁移脚本抄成一个新 revision**。这笔是永久的。
- 版本精确 pin（见 lockfile）。

至于它的表落在 `public` 而不是 `iclip`：它的 SQL 全是不带 schema 的裸名字，没有 `CREATE SCHEMA` 也不认 `search_path` 参数。要塞进 `iclip` 就得给它的连接一直配对的 `search_path`，多一处必须两边保持一致的配置——而这几张表本来就不是业务事实。

### 2. 提交也在后台，不在 HTTP 请求里

`POST /generations` 只做校验和落一行 `pending`，返回 202。真的去调外部接口是后台那几条队列的事。

这条是被图片接口逼出来的：它的「提交」就是生成本身，一次几分钟。留在请求里，客户端先超时，而那次生成还在扣钱。顺带也统一了两家的形状——同步接口在提交这一步就带回结果，于是「提交完已是终态」和「提交完还要等」是同一段代码的两个分支，而不是两条平行流程。

### 3. 三条队列，各自一个 worker

按「谁会拖住谁」切成三条：图片提交、视频提交、状态轮询。耗时差着数量级（300 秒 / 30 秒 / 1 秒），混在一条里，一批图片会把视频按在后面等。并发按「纯等待」定（各 100）：这两件事几乎整段时间都挂在对方的 socket 上，CPU 是空的。也不必为此加大数据库连接池——连接只在状态跳转那几毫秒里开合，从不跨着那次 HTTP 调用握着。真正的天花板在图像转存那一步：`oss2` 是同步 SDK，包在 `asyncio.to_thread` 里，受默认线程池（约 `CPU+4`）限制；上传成为瓶颈时要显式配执行器，而不是调这里的并发。

有一个哑巴故障要专门记住：**周期任务必须 defer 到有 worker 消费的队列上**。排到别的队列（包括它默认的 `builtin`）会永远躺在那儿，而且不报错。所以那个捡卡死任务的周期任务挂在轮询队列上。

### 3a. 「还在跑」借重试通道走，一个生成只占一行

每 5 秒 defer 一个新任务的话，一个生成一小时就往它的表里写七百多行。改成让任务抛 `StillRunning`、由我们自己的重试策略决定「5 秒后再来」，一个生成始终只占一行。**机械上它走的是重试通道，语义上它仍然不是失败**——因为那个策略是我们写的。

**这个策略不许设次数上限。** 界在任务体的第一句话，不在计数器：轮询撞上总时限就写终态并正常返回，提交重读那行看见 `submitting` 就判失败并正常返回——上限是**守卫**给的，所以每个任务最多多跑一次就自己停了。反过来在策略上设了上限，次数用完的任务会落在终态上，而它对应的那一行还停在 `submitting`：一次可能已经付过钱的生成，永远没有结论，也没人知道。

### 3b. 「还在跑」按固定间隔再问，不做逐次拉长的退避

退避看着更「懂事」，但账算下来是亏的：它省下的是几次廉价的状态查询，代价是**「做完了却没人发现」的延迟越拖越久**——而且拖得最狠的正是跑得最久的那些任务（那时已经退到了上限）。用户盯着进度条等的就是这个延迟。而「省下的调用」这一侧目前完全是猜测：我们既不知道对方的限流阈值，也不知道状态查询是否计费。用推测的收益去换确定的体验损失，不划算。

**唯一按更长间隔重排的情况是「问不通」**（网络断了、对方 5xx）：那时几百个在飞的任务每 5 秒重试一次只会让一个已经躺下的服务更起不来。

代价是固定间隔没有自我收敛的性质：一个永远说「在跑」的任务会被问到总时限为止。所以 `job_timeout_seconds` 是必需的兜底，不是可选项。真撞上限流再谈退避，届时该由对方明确告诉我们，不由我们先猜。

### 4. 时刻一律取数据库的时钟

多台应用服务器的时钟差几秒，「这次生成花了多久」「谁先写的」就都对不上——而这些是要拿去对账的。数据库只有一个，它的时钟没有「差几秒」这回事。

### 5. 不知道发出去没有，就判失败，绝不重投

两家接口都没有幂等键，重投一次就是重复付一次钱。所以：

- 调 provider **之前**先把状态落成 `submitting`。崩在响应回来之前，这一行就留在 `submitting` 上。
- **任务被重跑时，第一件事是重读那一行**：还是 `submitting` 就说明上一次崩在提交里了，**判失败**并写清原因，绝不重新提交。这次写入带状态守卫（只在它还是 `submitting` 时才落）：判断和写入之间隔着一次 await，那当口原来那个进程可能刚把真结果写完。守卫保证「谁有真结果谁说话」，绝不把一次已付费的成功盖成失败。
- **整套「重跑是安全的」就靠这个守卫**，不靠「不会重跑」。任务队列的保证是至少一次，我们不跟它较劲；我们保证的是「至少一次」不等于「付两次钱」。
- 提交阶段的失败一概是终态，连「网络超时」这种看着可重试的也不重试——请求可能已经落到对方那边，我们分不出来。
- **不替调用方换参数。** 模型（视频）与渠道（图片）都由请求带来；不同取值价钱不同，偷偷换一个等于悄悄改了这次花多少钱，与悄悄重投同类。一次调用，报错就是报错——错误码只负责让人分清「送到了没有」，不驱动自动动作。

这是本仓「伪造终态」禁令的同一条推理：事实不完整时只允许显式的、可重试的错误，把决定权交回人，不替他猜。不做失败后自动换渠道的回退：提交在后台队列里，「照实失败、让人重新发起」走得通，换渠道等于悄悄改了计费。

### 6. 进程死掉之后，任务怎么回来，分两种

只想着一种是会漏的：

- **优雅关停**（发版、重启）：宽限期到了会打断还在飞的任务，而被打断的任务是抛异常结束的，重试策略把它重排回待办。这一半不用我们管（实测过）。
- **硬杀**（SIGKILL、OOM、机器没了）：任务留在「有人在做」上，那个 worker 的心跳停了。**这一半必须自己捡**：procrastinate 自动维护心跳，但不会自动重跑——`get_stalled_jobs` 只是个查询，`retry_job` 是一次手动调用。所以有一个每分钟跑一次的周期任务干这件事。没有它，一次崩在提交里的生成永远停在 `submitting`，而它可能已经付过钱了。

关停宽限期不能设成无限：一次图像提交最长十几分钟，等它等于把整个进程的关停拖那么久，而部署环境的关停超时一到照样会杀进程——那时被打断的东西一样多，只是没人记下来。

顺带一条装配上的坑：**信号处理器归 uvicorn**，起 worker 时必须显式关掉 procrastinate 的（它默认装），否则两边都抢 SIGTERM。

### 7. 落行与排队不是原子的，所以排队失败要照实说

行走 asyncpg、队列走 psycopg，两个驱动就是两个事务，做不到原子（它能复用一个现成的连接池，但只能是 psycopg 的池）。所以：

- 排队这一步失败 → 把那行判失败（`QUEUE_DEFER_FAILED`）并把错误抛给调用方。**留一个「永远 pending」的行更糟**：那看起来像还在排队，而其实永远不会有人做它。
- 崩在两步中间 → 留下一个没有任务的 `pending` 行。罕见、看得见、由人重新发起。

**不为此建对账扫描。** 那个扫描就是「扫业务表找超时未推进的行」，也就是我们刚拆掉的那个轮子。这条和 `SUBMIT_INTERRUPTED` 是同一条道理：事实不完整时把决定权交回人。

### 8. 图片结果转存成自己的公开对象

图片接口给的是会过期的签名 URL，直接存库过几天就是烂链接。所以生成一到手就下载转存到公开对象存储（阿里云 OSS 官方 SDK，包在一个只有「写一个公开对象」的端口后面），库里存转存后的地址。

## 权衡

- **接受**：多一个数据库驱动（psycopg 与 asyncpg 并存）、多 30 个数据库对象、以及「升级它就要抄一个新 revision」这笔永久的维护费。换来的是那 400 行调度机械不再由我们维护——四个缺陷里的三个出在那一层。
- **接受**：入队不是事务性的（见 §7）。这也是 Postgres 队列最大的理论优势我们享受不到的地方。
- **接受**：轮询是拉模式，结果最晚会晚一个固定间隔（默认 5 秒）才被发现。改成 provider 回调会更即时，但那要开一个公网入口并处理它的鉴权与重放，本轮不值得。
- **接受**：worker 跑在 API 进程里。多进程本来就安全（心跳 + 领取都在库里），所以「以后拆成独立 worker 进程」是个部署选择，不是重新设计。
- **接受**：`submitting` 卡住的行会被照实判成失败，需要人来重新发起，不会自愈。这是刻意的——自愈的代价是可能重复计费。
- **接受**：视频结果直接存 provider 给的地址，不转存；图片转存是因为它明确会过期。
