# ADR-0003: agent 运行脱离 HTTP 请求，事件走可重放的流

- 状态：已接受（2026-08-23）
- **[ADR-0001](0001-architecture-foundations.md) §3（DB-based 运行）**：运行事实落库、恢复靠读库，是本文的前提。

## 背景

对话式创作里一次运行可能跑好几分钟。原来的做法是把运行绑在发起它的那次 HTTP 请求上：请求的响应体就是事件流，请求结束运行就结束。这带来三个躲不开的问题：

1. **用户切个页面、网络抖一下，运行就白跑了。** 浏览器断开连接，服务端的响应生成器随之被取消，运行也就断在半路。已经花掉的模型调用没有产出。
2. **断了接不回来。** 之前用的 Vercel AI 流协议只发 `data:`，既没有 SSE 的 `id:`，也没有任何游标或运行句柄，请求体里也没有可用来重新附着的 id。所以「从断开处接着看」在协议层面就无从实现（见 [../research/pydantic-ai-web-chat-ui.md](../research/pydantic-ai-web-chat-ui.md)）。
3. **多进程部署下重连没有着落。** 运行活在某个 worker 的内存里，重连的请求打到别的 worker 就什么都找不到。

## 决策

### 1. 协议换成官方 AG-UI

请求体是官方 `RunAgentInput`，客户端在里面给两个 id：会话 id（`threadId`）与运行 id（`runId`）。运行 id 让客户端有了一个能重新指认这次运行的名字，这是断线续读的前提。

协议的运行 id 与落库的 run_id 是**两套身份**：落库那个由官方 `StepPersistence` 自己派生（`{agent 名}-{短 uuid}`），拿协议的 id 去查主键查不到。但两者不是互不相认——协议的运行 id 会交给引擎（`run_stream(run_id=…)`），盖到这次运行的消息、快照与遥测上，所以事后对得上。会话维度靠 `threadId` 关联（它就是 `conversation_id`）。

### 2. 运行跑在请求之外，事件写进 Redis Stream

发起请求只做两件事：确保后台有个任务在跑，然后订阅事件流。二者之间除了 Redis 里那条流没有别的联系。于是客户端断开只是没人读了，运行照跑到底，结果照样落库。

每帧带上它在流里的位置，用标准 SSE 的 `id:` 发出去。客户端重连时把最后收到的位置放进 `Last-Event-ID` 头（浏览器原生 `EventSource` 会自动带），服务端从那儿接着发。

**帧一律编码成 SSE 存进流**，不看请求头的 `Accept`：整条流是可重放的，重放时必须给出和当初一样的字节，不能让先来的那个请求决定后来重连的人拿到什么格式。

### 3. 流的名字里带着归属

流名字是 `{用户 id}:{会话 id}:{agent id}:{运行 id}`。运行 id 是客户端自己起的，带上前面这两段之后它就只是「这个用户、这段对话里的一个名字」——猜别人的 id 落不到别人的流上，读不到就是 404；同一个人在两段对话里复用同一个运行 id 也不会串到一条流上。这样客户端提交的 id 不构成任何身份声明，不破「可信身份只来自宿主建立的 Principal」。

会话 id 由服务端发放、发消息时核对（见 [../architecture.md](../architecture.md)）；流名里带上它，防的是同一个人把两段对话的流搅在一起，与核对无关。

### 4. 断了就说断了，绝不编造结局

写流的后台任务定期续一个短命的存活标记。标记没了而流又没有终态事件，说明它没留下结局就消失了（进程被杀、被关停取消）。这时**读的人把一帧「中断了，可以重新发起」的 `RUN_ERROR` 写进流**收尾——写进流而不是只发给当前这个读者，是为了让所有人看到同一个结局。

同理，过了重放窗口再来续读，明确回 409 让客户端重新发起，绝不默默跳到当前位置假装接上了。

## 权衡

- **接受多一个基础设施依赖。** 声明了 agent 就必须配 Redis，缺了启动即报错。没有 agent 的部署不需要它（同 SSO：能力没配就不挂对应路由）。
- **接受「运行活在起它的那个进程里」。** Redis 让*流*与进程无关，重连打到哪个进程都能读；但正在跑的那个任务仍在起它的进程里，进程没了运行就断。这不是假装跑完的理由——按上面第 4 条收尾，客户端可以重新发起，历史快照在库里。真要做到进程无关地续跑，需要一个独立的任务队列，那是另一次决策。
- **接受活跃运行的流不做裁剪。** 裁了中间段，带游标来续读的人就会拿到一个有空洞的流而不知情。所以只在运行结束时给整条流定重放窗口；单次运行的事件数另有上限，超了就按可重试的中断收尾。
- **放弃 `Accept` 协商。** 见上，这是可重放性的代价。
