# ADR-0024：治理者复盘已删对话，删除不再清工作区

- 状态：已接受（2026-09-13）
- 修订 **[ADR-0021](0021-conversation-soft-delete.md)** 决策 1（删除仍先清工作区与素材台账）与决策 2（领域层只见活着的行），并推翻其取舍里「治理者的审计列表看不到已删对话」。
- 前提：**[ADR-0023](0023-governor-live-frames-and-done-state.md)** 决策 3 的信封字段做法（REST 端点贴、引擎不认识、前端按可选解析）。
- 合同 [§6 治理者复盘](../../contract/conventions.md#治理者复盘)随本文加 `deleted` 筛选与墓碑读取规则。

## 背景

治理者复盘的目的是找错误决策、给修正方案。被属主删掉的对话大多是生成失败的那一批，恰恰是最该看的样本；ADR-0021 却把它们从所有读口挡掉了，审计列表列不出，会话页按 id 也是 `404`。

更糟的是 ADR-0021 决策 1 沿用了旧流程：删除先物理清空工作区文件与素材台账，再标记 `deleted_at`。分镜文档与镜头 prompt 表都在工作区里，那正是决策失误最集中的地方。只放开读口的话，治理者打开一段已删对话会看到工具卡指向已不存在的文件、文件面板为空。

## 决策

### 1. 删除只标记，工作区与素材台账随墓碑留下

`DELETE /conversations/{id}` 只做 `SET deleted_at = now()`，不再调派生数据清理；`ConversationWorkspace.purge` 与两个存储的 `purge_namespace` 一并删掉，没有别的调用方。

留着无害：台账只约束工具在本对话里能用哪些素材，而没有任何写路径能到达墓碑；工作区按「属主 + 对话 id」分命名空间，配额也按命名空间算，id 永不重用，留着不会吃用户额度也不会撞名。

### 2. 墓碑只经治理者的读路径进入领域层

`Conversation` 加 `deleted_at`。仓储 `get` 加显式 `include_deleted`，缺省仍只见活行；不复用 `owner=None`，因为自动起名 `name_after_turn` 已用 `owner=None` 且必须只见活行。服务层用一个 `_readable` 收口读路径：持 `users:manage` 的主体按 `owner=None, include_deleted=True` 读，其他人按自己的活行读。经它的口子有 `header_of`、`agent_of(writing=False)`、`files`、`file`，WebSocket 的订阅与文件监听本来就走 `agent_of(writing=False)`，跟着放开且天然只读。

属主读自己的墓碑仍是 `404`；对话自身的写路径不变，再删一次仍 `404`。治理者读得到自己删掉的对话，但墓碑上对话自身的操作对谁都关着：治理者对自己墓碑的工作区覆盖写入是 `403`。删除不中止在跑的 run，墓碑可以合法地处于 busy；这几轮收尾时往对话上记 run 与自动起名会撞上墓碑，组合根捕获 `NotFound` 记一条 info，不当异常。

### 3. 审计加 `deleted` 三值筛选

`GET /conversations/audit` 收 `deleted`：`live`（缺省）/ `deleted` / `all`，照 `state` 的做法进同一组条件，列表与两个总数口径一致。缺省 `live` 让现有合同不变。这是唯一能列出墓碑的口；侧栏、搜索、需求单尝试列表都不收。

### 4. 游标索引收全部行，墓碑补回填

ADR-0021 让四个索引都只收活行，审计游标翻页依赖的 `ix_conversations_updated` 也在内，查墓碑就没索引可用。迁移 `0007_audit_deleted_conversations` 去掉这一个索引的谓词；属主视角的三个索引仍只收活行。0006 回填 `last_run_id` 时跳过了墓碑，墓碑在 `state=done` 下查不出来，0007 用同一条规则补上。

### 5. 对外形状

`ConversationOut` 加 `deletedAt`；`GET /transcript` 顶层加可选 `deleted_at`，与 ADR-0023 的 `owner_user_id` 同做法。前端审计筛选条加一组 chip「未删除 / 已删除 / 不限」，墓碑行标「已删除 · 时间」；会话页的只读判定加上「已删」，标签与说明改标「已删除」。

## 取舍

- **接受**：已经删掉的对话工作区在本决策之前就被清空了，找不回来；只有 Transcript 与生成任务可看。
- **接受**：0003 从票据补出来的老墓碑标题都是「已删除的对话」、无需求单归属，在列表里显得残缺，也匹配不上需求单筛选。
- **接受**：墓碑的工作区文件与素材行永久占存储。内部规模下几百段对话可忽略；将来要清就是显式的归档任务，不塞回删除流程。
- **接受**：治理者对自己墓碑的写路径答复不一致，工作区覆盖写入是 `403`、发消息与改名是 `404`。分界不是「读 vs 写」，而是 `write_file` 要先读整行拿属主拼命名空间，分得出「看得见但不能改」；其余写路径是带属主条件的单条 `UPDATE`，天然分不出。为统一口径给每次写多加一次读不值。
- **接受**：「墓碑只读」只覆盖对话自身的操作。生成任务的 `conversation_id` 是归档标签，生成域按 [ADR-0020](0020-generation-metadata.md) 不认识对话，属主删掉对话后仍能凭 id 往它下面挂新的出片记录；要挡要在生成受理层加对话可见性校验，会影响 API key 调用方，另开决策。
- **不做**：恢复接口与属主侧回收站。`deleted_at` 让它们成为可能，但不是这次的需求。
