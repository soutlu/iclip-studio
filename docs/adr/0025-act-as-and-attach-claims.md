# ADR-0025：钥匙替人办事，对话挂上需求单即认领

- 状态：已接受（2026-09-14）
- 修订 [CONTEXT.md](../CONTEXT.md) 运行依赖一节「归属标签不参与授权，也不决定行归属」，以及不变量 2 与禁止逻辑「信任客户端身份」的表述；需求单术语补「挂会话即认领」。
- 合同 [§2 双主体认证](../../contract/conventions.md#2-双主体认证-dual-principals)与 [§8 创作需求单](../../contract/conventions.md#8-创作需求单-tasks)随本文改写创建者、认领人的来源。

## 背景

机器调用方（partner_app 网关）拿一把 API key 替很多人提交：建需求单、开对话、发消息、出片。请求体里的 `user_name` 是替谁跑，但系统一直把它当标签，只发给上游落表；行归属一律记 key 属主。结果是 key 属主的侧栏堆满别人的活，真正的当事人在系统里连账号都没有；治理者审计看到的也全是 key 属主。网关建出来的需求单停在「待认领」、认领人为空，而它明明已经在被处理。

`user_name` 在上游眼里是真身份：图片网关按飞书在职名单校验它，名字对不上直接拒绝。所以它不该只是便条。

## 决策

### 1. 持 `users:act_as` 的 key 以 `user_name` 指名的人为主体

新增权限词 `users:act_as`，预置角色里只有 root 持有，机器 key 由签发者显式授予。四个写入口（建对话、建需求单、发消息、提交生成）拿到请求体后各调一次 `ActAs`：key 有这个权限并给了名字，就把 `Principal` 的 `user_id` 换成那个人、`username` 换成名字、`audit_label` 换成「名字#key 名」；`permissions` 与 `api_key_id` 原样保留。没有这个权限的 key 原样返回，名字仍只是标签，现网零变化。浏览器会话在这些字段里只能写自己的用户名。

规则只住在 `identity/acting.py` 一处；换出来的仍是同一份 `Principal`，下游属主校验、审计标签、运行重建都不用改。权限不继承被代理人，是为了报一个 root 的名字换不来 root 的权限。

能替任何人写的 key 也能读任何人的：对话读路径与生成记录的属主范围把 `users:act_as` 与 `users:manage` 同等放开（不含墓碑）。网关轮询状态、取文件用的是 key 自己的身份，没有这一条，属主一换它就读不到了。

### 2. 没有账号的人先建占位账号，本人 SSO 登录按用户名认领

用户名列本来唯一可空；邮箱列非空唯一，占位账号的邮箱按用户名确定性合成在 SSO 占位域下，随机密码谁也不知道，不给任何角色。两个请求同时报同一个名字靠唯一约束兜底，撞了重查。

SSO 回调原来按 SSO 唯一号、邮箱两步找人。在两步都没命中后加第三步：同名的占位账号存在就认领它，把占位邮箱换成真邮箱，再让 fastapi-users 按邮箱把 OAuth 账号挂上去，随后照首登给默认角色。SSO 回传的 `name` 与网关的 `user_name` 出自同一份飞书目录，所以按用户名精确匹配。真邮箱已属于另一个账号时不动占位号：那个账号若还没有用户名，同步资料时会撞名并记「显示名被占用」告警；若已有别的用户名则无声，占位号留给治理者在用户列表里发现并处理。

占位账号的建立与 SSO 认领必须同版上线，否则中间登录的人会另开一个新账号，占位号成孤儿。

### 3. 对话挂上需求单就是认领

需求单没有「进行中」状态，页面上的「进行中」就是 `confirmed`。对话挂到需求单下代表一次创作尝试，有人开了尝试就是有人在做。于是在对话挂上需求单的两条路（建对话带 `task_id`、`PUT /conversations/{id}/task` 给非空 id）之后，以对话属主认领那张单，走既有的 `confirm` 写入，它本来幂等。单子不在 `published` / `confirmed` 就不写也不报错：草稿没下发不可认领，挂会话不改变它。摘掉对话不清认领记录。

网关建单、开对话都传同一个 `user_name`，创建者与认领人自然一致；浏览器上从需求单开始创作也自动成为认领人。这绕过了原先认领所需的 `tasks:write`，只持 `agent:run` 的人开尝试即认领，是本决策的本意。

对话模块经组合根注入一个 `claim_task` 端口调需求单服务，模块之间不互相 import。

### 4. 有意推后

- 换主体只发生在请求体带 `user_name` 的四个写入口。同一把钥匙对占位账号名下对话的其他写操作（`:abort`、审批 `interactions/{id}`、steer、regenerate、`PUT /workspace/file`）仍以钥匙属主校验属主，会 `404` / `403`。网关今天只建单、开对话、发消息、轮询、取文件，没走到这些口；要走时给这些请求体补 `user_name`，或让持 `users:act_as` 的钥匙按对话行反查属主。
- 跨属主读取只对 `kind == "api_key"` 的主体放开，与 `ActAs` 只替钥匙换主体一致；浏览器用户直接授予 `users:act_as` 不会因此看到别人的对话。
- 不给对话、消息、需求单加 `api_key_id` 列。这三张表今天就分不清同一属主是在浏览器还是经 key 建的行，属于既有缺口而非本次引入；生成记录已有该列，日志标识带 key 名。
- 已记在 key 属主名下的旧数据不回填。生成记录里有 `user_name` 可追溯，对话与需求单上没有。
- `POST /tasks` 创建时的 `status` 取值不变，不收 `confirmed`；进入进行中由挂会话触发。

## 取舍

- 客户端字符串第一次决定行归属。收窄到一个显式权限、一个入口函数、权限不随之改变，并且能验证的地方（SSO 认领）按同一份目录精确匹配；名字打错会占住一个用户名，需治理者改名或转归属。
- 占位账号是真实的用户行，出现在用户列表里，没有角色也不能登录；治理者看得到它是谁替谁建的。
