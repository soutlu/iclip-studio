# ADR-0011: 上下文压缩——边界留在历史里，窗口发送时现算

- 状态：已接受（2026-09-04）
- 补充 **[ADR-0005](0005-transcript-protocol.md)**：「transcript 是消息的投影、不是事实源」在压缩之后继续成立，因为压缩不删消息。
- **[ADR-0006](0006-durable-runs.md)**：`StepPersistence` 的快照是模型历史的唯一事实源，是本文的前提。

## 背景

长任务几百步的工具循环会撞到模型窗口上限，运行时此前没有任何压缩。可选的做法分两派。

harness 的 `SummarizingCompaction` / `TieredCompaction` 一派**改写历史**：把旧消息删掉换成摘要，改动写回 run 历史，快照里从此只剩摘要。界面从快照推，被摘掉的轮子随之消失，轮号从消息数起算也会撞号；`TieredCompaction` 还会在中段原地涂黑工具结果，每触发一次就作废整段前缀缓存。

核心库自己是另一派：压缩是一条留在历史里的边界 part（`CompactionPart`），全量历史一条不删，模型看到的窗口在发送时从最后一条边界往后现算（`post_compaction_window`），UI 适配器把边界渲染成压缩标记。这与 agno 等框架「完整记录另存、只给模型发压缩后那段」是同一个模型。

核心库只在厂商自己返回边界时产生它，而且只有 Anthropic 与 OpenAI Responses 两个适配器在发送时按边界裁剪；Chat Completions 适配器遇到 `CompactionPart` 直接丢弃。百炼的 Responses 兼容接口只覆盖 qwen、没有压缩端点、缓存改为精确匹配，换适配器换不来原生压缩。

## 决策

### 1. 跟核心库的模型：边界留在历史里，不删消息

压缩发生时在切点插入一条 `ModelResponse([CompactionPart(content=摘要)])`，盖切点那条消息的 `run_id` 与压缩发生的时刻。盖切点的号而不是本次 run 的：这份历史下次交回引擎时，框架会把相邻的同角色消息并成一条，边界会并进它后面那次响应，而合并保留前一条的号，盖本次 run 的话那次响应连同它那一步会被拽进本轮。历史只增不改，快照是全量历史加边界，界面照旧从快照推，轮号、步号规则不变。

### 2. 缺的两段由我们补，都落在公开 hook 上

`harness/context_compaction.py` 一件能力：`before_model_request` 产生边界（这个 hook 的改动按框架设计写回 run 历史），`wrap_model_request` 把窗口交给 handler（这个 hook 只影响这一次请求，不写回历史）。窗口 = 紧跟 instructions 的一条 user 消息（摘要加一句「以上是二手信息」）+ 边界之后的全部消息。摘要不做 system part：chat 适配器把开头连续的 system 消息排在 instructions 之前，做成 system part 摘要会顶到 system prompt 前面；核心库原生压缩与 Claude Code 都把摘要放在 system 之后、对话开头。喂给摘要器的那份仍以 system part 装摘要，它认上一份摘要靠这个。不子类化适配器，不引用私有符号。将来 chat 适配器补上原生裁剪，这一层直接删。

### 3. 摘要复用 harness 的摘要器，只当黑盒用

`SummarizingCompaction.compact()` 提供调好的 prompt、增量更新与不拆工具对的切点；它自己的触发不挂。摘要器用主模型。摘要那次请求发的是历史的文本渲染，与对话请求没有共同前缀，本就命中不了缓存，换模型也一样。

### 4. 触发一次就压到底，中间只追加

触发线 `context_window × max_fraction`，尾巴留 `keep_messages` 条。两次压缩之间窗口逐字稳定，一次压缩一次缓存 miss。不挂任何原地涂黑历史中段的策略。

### 5. 界面上压缩是一块提示，不是一轮

挂在压缩之后第一步的首位，id `<步 id>.compaction`，不占块序号。历史路按边界的时刻找那一步，不按它在列表里的位置：边界插在切点，比它创建时正在跑的那一步早十几条。

## 取舍

- **存储按「不删」的代价走。** 每份快照都是全量历史；`max_snapshots_per_run` 管每次 run 留几份，对话级增长仍是 run 数乘历史长度。
- **压缩后模型要重新加载 skill。** 核心库从边界之后推导「模型看过什么」，之前加载的 skill 指令不再注入，模型按需再 `load_capability`。这是核心库对 Anthropic 原生压缩的同一处理。
- **重新生成不撤边界。** 边界盖的是切点那条消息的 run 号，末轮被撤时它留在原处，摘要里可能还提到被撤那一轮的前几步；下一轮的原文照常在窗口里，模型以原文为准。
- **压完请求就失败的那一次，界面上没有提示块。** 边界之后没有步可挂；模型侧压缩照常生效。
- **不用 receipt 与保留用户原话。** 窗口由一个 part 推出，这两样塞不进去；摘要之后加一句「以上是二手信息，关键事实回原文核对」代替。
